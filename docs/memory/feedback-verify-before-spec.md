2026-08-11 於 [[moe-indigenous-stats]] 確立，使用者兩次核准這個做法。

**做法**：走 spec-driven 流程（spectra 或任何規格先行的流程）時，**先實測資料端點
再寫提案**。提案裡的每個數字都應該是跑出來的，不是從目錄或文件推的。

**Why:** 第一次做反了——先照《產品總目錄》寫下「99–114 連續 16 個年度」，
提案、design、spec、tasks 四份都寫進去，實作時才發現開放服務端點只給最新一期，
四份 artifact 全部失效、要回頭改。第二次改成先取 oCode、先驗回傳內容再寫，
提案裡的 367／357／206／87 從第一版就是實測值，一路到 archive 沒有返工。

**How to apply:**

1. 提案前把端點打過一次：期別、粒度、欄位命名、筆數、失敗行為都看過。
2. 假設被推翻時，**不要拿失效的 spec 硬寫程式**。先修 artifact（spectra 有
   `/spectra-ingest` 專門處理需求中途變動），再回來實作。
3. 實作中發現 spec 沒涵蓋的問題（例如「標準化值建立在不穩定的格子上」），
   **補一條 requirement 再改程式**，不要只默默改程式。
4. 範例表就是測試案例——**裡面的數字不可以是估的**。曾把「有原民生的鄉鎮」
   填 83（沒實算），實際是 86；錯的範例會變成錯的驗收。
5. 自己先前講錯的結論要主動更正並說清楚依據，不要讓它留在對話裡當前提。
