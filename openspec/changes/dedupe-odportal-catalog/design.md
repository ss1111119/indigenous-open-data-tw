## Context

`catalog/odportal-763-graded.csv` 是編目層（`README.md`「這是什麼」的第一層）的主要產出，763 筆資料集各帶品質分級。其中 160 筆的 `與其他資料集共用資源` 欄指向另一筆資料集，但分級階段只記下這個訊號，未查明關係，故 `docs/來源盤點.md` 一直記著「合併規則未定」。

2026-08-13 查明並記入 `docs/來源盤點.md` 第五節「那 160 筆到底是什麼」：是同一份資料上架在中央的政府開放資料平臺與地方入口網，名稱與資源 `rid` 相同。

**現有約束**：

- 環境已具備 Python 3.13.9、pandas 3.0.0，本變更不新增第三方套件
- 輸入為既有的 `catalog/odportal-763-graded.csv` 與 `data/raw/catalog/odportal-resources.json`，本變更不連網
- `data/raw/` 不入版控，故腳本必須能在只有分級清單的情況下明確報錯，而不是靜默產出殘缺結果
- 專案原則：安全網釘跨檔案不變量，不釘單一數字

**已實測確認的結構**（2026-08-13，皆為跑出來的數字）：

- 160 條共用指標**全部指向 763 之內**，無懸空指標
- 連通分量為 603 個單筆群 ＋ **80 個雙筆群**，無三筆以上的群
- 去重後恰為 **683 筆**
- **23 群**聚集後的資源數超過任一成員原本的數量

**已實測確認的欄位衝突分佈**（80 個成對群）：

| 欄位 | 兩側相同 | 一側有值一側空 | 兩側皆有值但不同 |
| ---- | -------: | -------------: | ---------------: |
| `提供機關` | 0 | **80** | 0 |
| `分級` | 79 | 0 | **1** |
| `名稱` | 74 | 0 | **6** |
| `授權` | 73 | 1 | **6** |
| `來源平台` | 0 | 0 | **80** |
| `格式` | 40 | 0 | **40** |

## Goals / Non-Goals

**Goals:**

- 產出去重後的清單，同一份資料只佔一列
- 合併不掉任何資源網址
- 每個欄位的合併規則都有實測依據，而非任意取捨
- 明確標示哪些列的分級欄位未涵蓋合併後新增的資源
- 以不變量測試釘住「不掉資源」與「筆數關係」

**Non-Goals:**

- **不重新探測資源。** 代價是又一波對政府主機的請求，且會使分級結果與已發佈的 `catalog/品質分級報告.md` 不一致。改以旗標欄標示未涵蓋範圍
- **不改寫 `catalog/odportal-763-graded.csv`。** 「763」出現在多份文件，改寫會使既有敘述失效
- **不做 SEGIS 與 ODPortal 的跨清單去重。** 兩份清單的識別欄位不同，需另行設計
- **不做跨機關口徑統一。** 去重處理「同一份資料被索引兩次」，與「機關間定義不一致」是不同問題
- **不攤平任何資料集內容。** 產出仍是清單，不是長表

## Decisions

### 以連通分量分群，不做兩兩配對

`與其他資料集共用資源` 欄只存單一夥伴 id。實測目前全部是雙筆群，兩兩配對在今天可行。

但採用連通分量（union-find）：若上游日後出現三筆互指，兩兩配對會產生互相矛盾的合併結果（A 併 B、B 併 C，A 與 C 卻分屬兩列），且不會報錯。連通分量在同樣情況下自然併為一群。

同時斷言「群大小不超過 2」——今天成立，若日後不成立則報錯而非靜默改變行為。

**替代方案**：兩兩配對。已否決——今天可行但缺乏對上游變化的抵抗力，且錯法是靜默的。

### 資源取聯集，不選單一贏家

實測 46 筆兩邊各有對方沒有的資源，選任一邊都會掉資料；平台優先序無效，中央較全與地方較全各佔約一半。落差最大達 10 倍（`10730-09-01-2 臺中市原住民權益及福利宣導統計` 中央 183 個資源、臺中市平台 18 個）。

決策：合併後的資源集合為各成員資源網址的聯集，`資源數`、`資源總數` 依聯集重新計數。

**替代方案**：留資源較多的那筆。已否決——對 46 筆而言是有損的，且損失無法從輸出察覺。

### 各欄位的合併規則依實測衝突分佈決定

| 欄位 | 規則 | 依據 |
| ---- | ---- | ---- |
| `提供機關` | 取有值的那側 | 80/80 是一側有值一側空，零例外。中央平台那筆此欄為空 |
| `名稱` | 取 `提供機關` 有值那側 | 6 筆名稱不同者皆為桃園的命名慣例差異；地方是資料實際提供者，其命名較貼近來源 |
| `來源平台` | 兩者並列，以 `;` 連接後排序 | 80/80 不同，因為「上架在兩個平台」正是被合併的事實本身，不該丟掉任一個 |
| `格式` | 取聯集，以 `;` 連接後排序 | 40 筆不同者為中央宣告 `JSON;CSV;XML`、地方僅宣告 `JSON`。格式標示本不可信，聯集最無損 |
| `授權` | 取具體值，捨棄 `UNKNOWN` 與空值 | 6 筆衝突皆為 `OGDL-1.0` vs `UNKNOWN`，具體值明顯是較有資訊的一方 |
| `最後更新` | 取較新者 | 合併後的資料集涵蓋兩側資源，最後更新時間應為兩者中較新的 |
| `分級` | 取較可用者，並設旗標 | 僅 1 筆衝突（`真資料` vs `網址無效`）。聯集後該筆確實含可用資源，故取 `真資料`；但兩側判斷不一致這件事必須留痕 |

`ODPortal`、`原始網址` 兩欄各成員不同，合併後保留 `提供機關` 有值那側者，另立欄位記錄全部成員的 id 以便回溯。

**替代方案**：衝突一律報錯要求人工裁決。已否決——127 個衝突欄位值需要逐一裁決，而其中 126 個有明確的實測規則可循；只有分級那 1 筆需要留痕，用旗標即可。

### 分級未涵蓋新增資源以旗標欄標示，不重新探測

23 群聚集後的資源數超過任一成員原本的數量，這些列的 `最大記錄數`、`檔案類欄位`、`實際型態` 是舊樣本的結果，未涵蓋新增資源。分級本身也只取每個資料集最多 2 個代表性資源為樣本。

決策：新增布林欄 `分級未涵蓋新增資源`，於這些列為真。

⚠️ 這與 C 系列長表「不加 flag 欄」的決策方向相反，理由不同：C 系列的 `-` 經實測證明就是 0，flag 會標記一件沒發生的事；此處旗標記錄的是**取樣範圍的真實限制**，是關於信心的中介資料，不是要使用者過濾的值。姊妹專案 `moe-indigenous-stats` 的 `人數過少` 亦屬此類。

**替代方案**：重新探測使欄位完整。已否決——見 Non-Goals。

### 保留原清單，另出新檔

新增 `catalog/odportal-deduped.csv`，`catalog/odportal-763-graded.csv` 不動。

「763」出現在 `README.md`、`catalog/品質分級報告.md`、`docs/來源盤點.md` 多處；改寫原檔會使這些敘述同時失效，且去重前的狀態只存在於 git 歷史。兩份並存的代價是需要說明兩者關係，這寫在報告與盤點文件裡即可。

**替代方案**：改寫原檔。已否決——見上。

## Implementation Contract

**行為**：執行去重指令後，`catalog/odportal-deduped.csv` 產生 683 列。重跑產生位元組相同的輸出。不發出任何網路請求。

**資料形狀**：保留 `catalog/odportal-763-graded.csv` 的全部既有欄位，並新增三欄：

- `合併筆數`：整數，未合併者為 1，合併者為 2
- `合併來源`：字串，該列所有成員的 ODPortal id，以 `;` 連接後排序；未合併者為自身 id
- `分級未涵蓋新增資源`：布林，聯集後資源數超過任一成員原本數量者為真

`資源數` 與 `資源總數` 依聯集後的資源網址重新計數。`來源平台` 與 `格式` 為 `;` 連接的排序後聯集。

**指令介面**：單一指令，讀既有清單與資源 json，寫出去重清單。輸出路徑可以參數覆寫。

**失敗模式**（皆為阻斷性錯誤，不設靜默降級路徑）：

- 共用資源指標指向清單外的 id → 報出該 id 與來源列
- 連通分量出現三筆以上的群 → 報出該群成員，因為合併規則的實測依據只涵蓋雙筆群
- 某群的 `提供機關` 兩側皆有值且不同 → 報出雙方值，因為實測顯示應為一側有值一側空
- 找不到 `data/raw/catalog/odportal-resources.json` → 報出路徑與重新取得的指令
- 聯集後的資源數小於任一成員原本的資源數 → 報錯，這代表聯集邏輯有誤

**驗收標準**：

- 輸出恰為 683 列，且 `合併筆數` 為 2 的列恰為 80 列
- 輸出的資源網址聯集與輸入 763 筆的資源網址聯集完全相同（不多不少）
- `分級未涵蓋新增資源` 為真的列恰為 23 列
- `提供機關` 在合併列上皆非空
- 連續兩次執行產生位元組相同的輸出
- 測試對「不掉資源」與「筆數關係」兩項注入故障後會失敗

**範圍界線**：

- 在範圍內：ODPortal 763 筆清單的去重、合併規則、旗標欄、測試、報告與盤點文件更新
- 在範圍外：重新探測、改寫原清單、SEGIS 跨清單去重、跨機關口徑、任何資料集內容的攤平

## Risks / Trade-offs

- **兩份清單並存會被誤用**：使用者可能拿舊清單當最新 → 在 `catalog/品質分級報告.md` 與 `docs/來源盤點.md` 明寫兩者關係與各自用途，並在去重清單的檔名中以 `deduped` 標明性質

- **合併規則的實測依據只涵蓋當前這批資料**：規則來自 80 個成對群的分佈，若上游改變上架方式，分佈可能不同 → 每條規則的例外情形都設為阻斷性錯誤（例如 `提供機關` 兩側皆有值），使規則失效時報錯而非靜默套用

- **分級欄位在 23 列上不完整**：旗標標示了範圍限制，但使用者仍可能忽略 → 旗標欄名直述其意（`分級未涵蓋新增資源`），且在報告中說明為何不重新探測

- **`最後更新` 取較新者可能不反映實情**：若較新的那側其實只更新了 metadata 而非資料，取較新者會高估新鮮度 → 影響僅為單一欄位的樂觀偏差，且該欄位在編目層只用於粗略判斷，不作為分析依據

- **80 個成對群幾乎全是臺中市**：規則主要由一個縣市的上架習慣推導而來 → 桃園、臺北的少數案例已納入衝突分佈統計並符合同一規則；且例外情形皆為阻斷性錯誤
